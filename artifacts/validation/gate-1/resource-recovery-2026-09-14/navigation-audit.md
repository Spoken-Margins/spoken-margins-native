# Navigation and compute audit — September 14, 2026

Code audit of `codex/provisional-next`, base `ad533d6` plus existing changes. No implementation changes or tests in this audit. Owner reports internal iPhone 14 PDF Timeline Back becoming unresponsive during suspected rendering, requiring force quit. Internal source is recorded as `adeb923`; key back-action, fingerprint, import and progress paths were also found there. No iPhone 14 trace or measured navigation latency is available. This inventory covers the inspected app orchestration and speech/persistence paths, not proof that every possible performance defect has been found.

## Model and evidence boundary

Navigation/button handling and UI updates share the main actor. There are three distinct failure mechanisms: synchronous work occupies it; synchronous reads wait for shared storage locks; off-main work competes for CPU, memory and I/O. Broad observation amplifies any of these by scheduling unnecessary UI work. A separate fourth possibility is a state guard intentionally rejecting navigation. “Background” in a function name or an async Task does not establish that synchronous work runs outside the main actor.

The Timeline toolbar action calls `returnToPlayback` (ExperienceTimelineRailScreen.swift:400), which calls `openPlayback` within an animation. `openPlayback` (Gate1AppModel.swift:5091) checks recording permission and active session, assigns the screen, and can synchronously load a different active item. There is no rendering-disabled guard. If selected and active items match, that detail load is skipped. Thus main-actor blockage/invalidation is a leading hypothesis, while stale permission/session state is an alternative to test. The prior passage-boundary fix does not address this navigation issue.

## Confirmed cost sites, ordered for remediation

1. **Per-chunk full Library reconstruction.** `performBackgroundAudioPreparationPass` ends by calling `refreshLibraryRows` (Gate1AppModel.swift:14611 vicinity). That main-actor method (10688) loads Library rows, deleted items and queue presentation. `loadLibraryRows` (10532) reads all items, sessions, manifests, jobs and downloads. `refreshAudioPreparationPresentation` (10703) repeats several whole-collection reads and performs queue housekeeping. `listItems` reads complete JSON item payloads, not a lightweight metadata projection (SQLiteSessionStore.swift:604). This can hitch any visible screen after each chunk. Fix: incremental changed-item/queue updates, metadata-only queries and off-main snapshot preparation; no full refresh per chunk.

2. **Repeated model fingerprinting and full-source planning.** Each Library pass computes `SupertonicRenderIdentity.make` and `preparedChunkPlan` (Gate1AppModel.swift:14494,14504). Hashing is detached, but `treeHash` concatenates every model file into one Data allocation (PreparedAudioCoordinator.swift:52). The locally built model directory occupies about 138 MB; this is an asset-size observation, not a measured process-memory peak. Fix: stream the identical digest byte sequence and reuse a fingerprint for the immutable installed model assets; cache the exact source/signature chunk plan. Preserve identity compatibility and invalidate on asset/source changes. This also strengthens the memory-pressure investigation.

3. **Broad screen invalidation.** Gate1AppModel is a main-actor ObservableObject with published playback, diagnostics, preparation and Library state (516 onward). Timeline and root consume it as EnvironmentObject. The 500 ms playback ticker (1619) and chunk state/progress updates (8650,8666) publish changes. Even diagnostic-only changes can invalidate subscribers. Fix: separate transport/preparation/diagnostic observation, publish only meaningful changes, and coalesce presentation updates. Keep progress truthfulness and audio scheduling independent of presentation throttling.

4. **Navigation-time persistence and projection.** Home (4911) synchronizes playback, loads selected-item data through lifecycle sync (1673), and refreshes the Library before assigning the screen. Playback (5091) can load item detail after assignment, still in the same synchronous action. SwiftUI cannot display the new screen until that action yields. Fix: navigation changes immediately against an existing snapshot; refresh asynchronously without losing the saved playhead or allowing stale results to replace a newer selection.

5. **Timeline and detail rebuilding.** Timeline recreates all entries on every selectedItem publication (ExperienceTimelineRailScreen.swift:65,69,338); lazy rows and equatable row views do not remove this upstream work. `loadItemDetail` (Gate1AppModel.swift:14108) loads/project chapters, maps, sessions, notes, turns and imported layers, including per-session note reads. Fix: structural revision keys, immutable cached projections and batched queries; playhead-only updates should not rebuild the rail. Measure large PDFs and shared-Margin sessions separately.

6. **Shared database contention.** SQLite query execution and JSON decoding hold one connection lock (SQLiteSessionStore.swift:739,994). Main-actor reads can wait behind worker activity, even when that activity is off-main. No deadlock is proven. Fix: asynchronous storage access from UI paths and bounded projections/transactions; evaluate separate read access only with explicit consistency rules.

7. **Import completion on the main actor.** PDF baseline extraction is already detached (Gate1AppModel.swift:3233,3270), but `importBrowserTextInBackground` (3294) synchronously sanitizes/imports through the engine and rebuilds Library rows. Pasted assistant response import (7078) parses/imports, refreshes detail and changes screens synchronously. Fix: prepare text/maps off-main, commit safely, then publish a small result. Preserve active playback and source offsets. Do not move an entire mutable SessionEngine into a detached task.

8. **Speech startup, seek and renderer bookkeeping.** `prepareSpeechText` normalizes the full source synchronously (SupertonicSpeechPlaybackClient.swift:603); new requests build a complete chunk plan (1140). The render task copies the entire generation plan again for every chunk (1214), even though the preparation callback only needs the full plan initially. Fix: cache source projections/plans and eliminate per-chunk whole-plan copies. Keep intentional seek/cancellation behavior covered.

9. **Prepared-audio completion.** Assembly itself has a worker path, but completion performs canonical text/segment conversion, attaches persistent audio, refreshes Library/detail, and updates edition data on the main actor (Gate1AppModel.swift:10292,9961,14677). This can produce a large hitch exactly when rendering reaches 100%. Fix: calculate immutable attachment data off-main and publish bounded changes after a safe commit.

10. **Listening Map generation and transcript checkpoints.** `runEpisodeMapPreparation` creates a Task in the main-actor model (4007) then synchronously hashes the downloaded episode (4020), reads checkpoint files and decodes/encodes transcript data (4120 onward). Network/transcription awaits do not move the surrounding synchronous operations off-main. Fix: bounded file/hash/JSON workers and small checkpoint updates. This can affect navigation even while viewing a different item.

11. **Export, sharing and summary preparation.** Opening Export immediately builds/renders the export and may write Markdown synchronously (6457). Summary setup loads source/notes and refreshes detail before/after dispatching generation (6205). Sharing actions route back through the same model. Export is a confirmed synchronous cost; the full sharing/summary pipeline needs a deeper trace before assigning a dominant cost. Fix: show the destination immediately with cancellable preparation, never make Back wait for output generation.

12. **Aggregate worker pressure.** Supertonic inference is on a serial queue, audio assembly is worker-based, and PDF extraction is detached: do not mislabel those as main-thread inference. However, serial Supertonic execution is not a global compute budget; import, map/transcription and hashing can coexist. ONNX session construction uses default thread options (SupertonicRuntime.swift:861). Fix priority is removing redundant work above; then measure concurrency/thread limits against both frame latency and audio underruns. Do not automatically lower voice quality or halt every useful task whenever the user scrolls.

## Decision and verification

First repair the shared per-chunk refresh/fingerprint path and navigation-time synchronous loads, then isolate observation and structural projections. These affect many screens and plausibly fit the report. Follow with import/completion/map/export boundaries. The previous memory-warning hardening alone is insufficient.

Proposed responsiveness contract for owner acceptance: Back, tab switches and Cancel remain operable during rendering/import/map work. Proposed measurable targets are visible tap feedback within 100 ms and a navigation update within 250 ms on the target iPhone 14; these are candidate product budgets, not measured results or Apple requirements. Audio must continue without position loss, unintended fallback or render-queue deletion.

Minimum discriminating check: same PDF/Library on iPhone 14, (A) fully prepared, (B) actively rendering, (C) completing rendering. Capture back-action entry, screen assignment, main-actor spans around Library/detail work and Instruments main-thread stacks. If the handler never starts, inspect main-thread occupancy; if it starts and exits a guard, inspect permission/session state; if it assigns screen quickly but display remains frozen, inspect view/layout/animation work. A second check while returning Home differentiates the separate pre-navigation refresh path. Sample memory during hashing to test the 138 MB accumulation hypothesis.

Omission check: explicitly exercise Timeline Back, edge-back/Home, Library tabs, Item/Now Playing, export dismissal, modal Cancel, import completion and map completion. Confirm source progress and existing recording-navigation safeguards survive. Stop after one actionable trace or a focused regression that falsifies a candidate; do not repeat broad suites for an audit. Full release tests remain deferred until the owner requests internal distribution.
